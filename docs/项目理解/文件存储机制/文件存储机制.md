# OpenVSCode Server 文件存储机制分析

## 概述

本文档详细分析了 OpenVSCode Server 项目中客户端文件存储和缓存机制，包括存储方式、加载策略以及客户端与远端服务器的同步机制。

---

## 一、存储方式：IndexedDB vs localStorage

### 核心结论

**文件内容缓存到 IndexedDB，而不是 localStorage。**

### 1. IndexedDB 用于文件系统缓存

在 `web.main.ts` 中，文件系统提供者使用 IndexedDB：

```typescript
// 创建 IndexedDB 数据库用于文件系统
IndexedDB.create('vscode-web-db', 3, [
    userDataStore,      // vscode-userdata-store
    logsStore,          // vscode-logs-store
    handlesStore        // vscode-filehandles-store
])
```

**数据库结构：**
- **数据库名**：`vscode-web-db`
- **版本**：3
- **存储空间（Stores）**：
  - `vscode-userdata-store`：用户数据
  - `vscode-logs-store`：日志数据
  - `vscode-filehandles-store`：文件句柄

**文件内容存储：**
- 使用 `IndexedDBFileSystemProvider` 处理文件系统操作
- 文件内容以 `Uint8Array` 形式存储在 IndexedDB 中
- 支持大文件存储（IndexedDB 容量远大于 localStorage）

### 2. IndexedDB 用于存储服务

应用状态和配置也存储在 IndexedDB 中：

```typescript
// 存储服务使用多个 IndexedDB 数据库
- vscode-web-state-db-global          // 全局状态
- vscode-web-state-db-global-{profileId}  // 特定配置文件的全局状态
- vscode-web-state-db-{workspaceId}   // 工作区状态
```

### 3. localStorage 的有限使用

localStorage 仅用于少量简单的键值对配置：

- **配置项**：locale（语言设置）、splash screen（启动画面）等
- **URL callback 机制**：处理 OAuth 回调等
- **Secret storage**：加密后的密钥存储
- **Broadcast channel 降级方案**：当 BroadcastChannel API 不可用时的备选方案

**为什么使用 IndexedDB 而不是 localStorage？**

1. **容量限制**：localStorage 通常只有 5-10MB，而 IndexedDB 可以存储数百 MB 甚至 GB 级数据
2. **性能**：IndexedDB 支持异步操作，不会阻塞主线程
3. **数据类型**：IndexedDB 可以存储二进制数据（Uint8Array），适合文件内容
4. **结构化存储**：IndexedDB 支持索引和查询，更适合复杂数据结构

## 二、文件加载策略：懒加载 vs 预加载

### 核心结论

**文件是懒加载（按需加载）的，不是全量预加载。**

### 1. 文件加载时机

文件仅在以下情况从服务器读取并缓存到 IndexedDB：

- ✅ **在编辑器中打开文件时**
- ✅ **扩展或功能需要读取文件时**（如搜索、语言服务等）
- ✅ **用户显式访问文件时**

### 2. 文件加载流程

```typescript
// 文件工作副本管理器
class StoredFileWorkingCopy {
    async resolve(options?: IStoredFileWorkingCopyResolveOptions): Promise<void> {
        // 1. 检查文件是否已解析
        if (this.isResolved()) {
            return;
        }
        
        // 2. 从服务器读取文件
        const stream = await this.fileService.readFileStream(this.resource);
        
        // 3. 将文件内容缓存到 IndexedDB
        // 4. 更新工作副本状态
    }
}
```

### 3. 预加载机制（特殊情况）

存在一个特殊的预加载机制，但仅适用于特定场景：

```typescript
// 仅针对 vscode-vfs scheme 和 github authority
// 且需要 SharedArrayBuffers 支持
startPreloadWorkspaceContentsIfNeeded()
```

**注意**：这个预加载机制不是默认启用的，只在特定条件下才会触发。

### 4. 缓存范围

**不会缓存的内容：**
- ❌ 未打开的文件
- ❌ 未访问的文件
- ❌ 工作区中但从未读取的文件

**会缓存的内容：**
- ✅ 已打开的文件内容
- ✅ 已读取的文件内容
- ✅ 用户数据（配置、扩展数据等）
- ✅ 日志数据

## 三、客户端与远端服务器的同步机制

### 核心机制

客户端缓存与远端服务器通过以下机制保持同步：

1. **ETag 机制**：检测文件是否被修改
2. **文件变化监听**：实时监听远端文件变化
3. **自动重新加载**：检测到变化后自动更新
4. **冲突处理**：保存时检测并处理冲突

### 1. ETag 机制（文件版本检测）

**ETag 生成规则：**

```typescript
// 基于文件的修改时间和大小生成 ETag
function etag(stat: { mtime: number; size: number }): string {
    return stat.mtime.toString(29) + stat.size.toString(31);
}
```

**ETag 的作用：**
- 唯一标识文件版本
- 检测文件是否被修改
- 避免不必要的文件读取（304 Not Modified）

**工作流程：**
1. 首次读取文件时，服务器返回文件内容和 ETag
2. 客户端将文件内容和 ETag 一起缓存到 IndexedDB
3. 再次读取时，客户端发送 If-None-Match 头（包含缓存的 ETag）
4. 如果文件未修改，服务器返回 304，客户端使用缓存
5. 如果文件已修改，服务器返回新内容和新的 ETag

### 2. 文件变化监听

**监听机制：**

```typescript
// 文件服务监听文件变化
fileService.onDidFilesChange((e) => {
    // 处理文件变化事件
    // 1. 检查文件是否在编辑器中打开
    // 2. 检查文件是否处于 dirty 状态（有未保存的修改）
    // 3. 如果文件不是 dirty，自动重新加载
})
```

**监听范围：**
- 工作区内的文件变化
- 通过文件系统提供者（FileSystemProvider）监听
- 支持轮询和事件驱动两种方式

### 3. 自动重新加载策略

**重新加载条件：**

| 文件状态 | 远端变化 | 行为 |
|---------|---------|------|
| 未打开 | 变化 | 不处理（文件未加载） |
| 已打开，无本地修改 | 变化 | ✅ **自动重新加载** |
| 已打开，有本地修改（dirty） | 变化 | ⚠️ **提示用户选择** |

**自动重新加载流程：**

```typescript
// 当检测到文件变化时
if (fileIsOpen && !fileIsDirty) {
    // 自动重新加载文件
    await fileWorkingCopy.resolve({ 
        force: true  // 强制重新读取
    });
}
```

### 4. 冲突处理机制

**保存时的冲突检测：**

```typescript
// 保存文件时
async save(options?: IStoredFileWorkingCopySaveOptions): Promise<boolean> {
    // 1. 检查文件是否已被修改（通过 ETag）
    const stat = await this.fileService.resolve(this.resource);
    
    if (stat.etag !== this.lastSavedETag) {
        // 2. 文件已被修改，进入冲突处理
        throw new FileOperationError(
            'FILE_MODIFIED_SINCE',
            FileOperationResult.FILE_MODIFIED_SINCE
        );
    }
    
    // 3. 保存文件
    await this.fileService.writeFile(this.resource, content);
}
```

**冲突处理选项：**

当保存时检测到文件已被修改，系统会：

1. **提示用户选择**：
   - 覆盖远端文件（使用本地版本）
   - 使用远端文件（丢弃本地修改）
   - 比较差异（手动合并）

2. **自动处理策略**（如果配置）：
   - 自动覆盖
   - 自动使用远端版本

## 五、总结

### 存储方式
- ✅ **IndexedDB**：用于文件内容、用户数据、日志等大量数据
- ⚠️ **localStorage**：仅用于少量简单配置

### 加载策略
- ✅ **懒加载**：按需加载，只缓存打开/访问的文件
- ❌ **预加载**：默认不预加载，只在特定条件下启用

### 同步机制
- ✅ **ETag**：检测文件版本，避免不必要的读取
- ✅ **文件监听**：实时监听远端文件变化
- ✅ **自动重新加载**：文件未修改时自动更新
- ✅ **冲突处理**：保存时检测并处理冲突

### 优势
1. **性能优化**：懒加载减少初始加载时间
2. **存储效率**：只缓存需要的文件
3. **同步可靠**：ETag + 文件监听确保数据一致性
4. **用户体验**：自动处理文件变化，减少手动操作
